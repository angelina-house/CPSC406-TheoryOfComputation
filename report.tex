  # dfa.py
  class DFA:
      def __init__(self, Q, Sigma, delta, q0, F):
          self.Q = Q  # Set of states
          self.Sigma = Sigma  # Alphabet
          self.delta = delta  # Transition function
          self.q0 = q0  # Initial state
          self.F = F  # Accepting states
  
      def __repr__(self):
          return f"DFA({self.Q},\n\t{self.Sigma},\n\t{self.delta},\n\t{self.q0},\n\t{self.F})"
  
      def run(self, w):
          current_state = self.q0
          for symbol in w:
              if symbol not in self.Sigma:
                  return False
              current_state = self.delta.get((current_state, symbol))
              if current_state is None:
                  return False
          return current_state in self.F  # Accept if in accepting state
  
      def refuse(self):
          # new dfa that refuses input
          return DFA(self.Q, self.Sigma, self.delta, self.q0, set())

\subsubsection*{Reading Summary and Questions}

Section 2.2 focuses on Deterministic Finite Automata (DFA), which are computational models used to process input strings and determine whether they belong to a specific language. 
A DFA consists of a finite set of states $Q$, a defined input alphabet $\Sigma$, transition rules $\delta$ that 
dictate how the automaton moves between states, a starting state $q_0$, and one or more accepting states $F$ that signify valid inputs.
The operation of a DFA is systematic: it begins in the initial state and processes an input string one symbol at a time, following a unique transition for each symbol. 
Once the entire input has been read, the DFA determines acceptance based on its final state. If it ends in an accepting state, the input is considered valid; otherwise, it is rejected.
Formally, a DFA is defined as a five-tuple $(Q, \Sigma, \delta, q_0, F)$, where $Q$ is the set of states, $\Sigma$ is the input alphabet, $\delta$ is the transition function that maps 
states and inputs to new states, $q_0$ is the initial state, and $F$ is the set of accepting states. 
DFAs are widely used in applications such as text searching, lexical analysis in programming, and pattern recognition. Their deterministic nature makes sure that for any given input, 
the transition path is unique making them both predictable and efficient for structured data processing.

\subsection*{Reading Summary and Questions}

Section 2.3 covers Nondeterministic Finite Automata (NFA) and how they differ from Deterministic Finite Automata (DFA). The key difference is that, unlike a DFA where each state has exactly one transition per input, 
an NFA allows multiple possible transitions, or none at all, for the same input symbol. This make an NFA capable of following multiple computational paths at once, making it more flexible. A string is accepted if at least one 
of these paths leads to an accepting state. The section also introduces the extended transition function, which determines all the possible states an NFA can reach after processing a string. NFAs recognize the same class of 
regular languages as DFAs. Any NFA can be converted into an equivalent DFA using the subset construction method but, this process can significantly increase the number of states, sometimes exponentially. Regardless, NFAs are 
often more compact and easier to construct, making them useful in applications like pattern matching and lexical analysis. While DFAs and NFAs are equivalent in terms of what they can recognize, NFAs provide a more 
convenient and flexible approach to defining automata.

\subsection*{Reading Summary and Questions}
Section 4.4 covers how to determine if two deterministic finite automata (DFAs) are equivalent and how to simplify a DFA by minimizing it. Two DFAs are considered equivalent if they accept exactly the same set of strings, 
meaning they recognize the same language. One way to test this is by creating a new DFA that accepts only the strings where the original two DFAs disagree—if this new DFA accepts nothing, then the two are equivalent. 
The section also introduces a process for minimizing a DFA by merging states that behave the same for all inputs. This is done using the table-filling algorithm, which helps identify indistinguishable states—those that can’t 
be told apart by any string. Once the indistinguishable states are grouped, a new, smaller DFA is created that still accepts the same language. This minimized DFA is guaranteed to be the smallest possible version for that language 
and is unique up to state naming. Minimizing DFAs is helpful in real-world applications like text processing, search algorithms, and compiler design because it makes the automaton more efficient. Overall, Section 4.4 provides 
practical techniques for comparing and simplifying DFAs while ensuring their behavior stays the same.

Sections 8.1 and 8.2 explore the limits of what computers are capable of. Section 8.1 introduces the idea of undecidable problems—problems that no program can solve 
for every possible input. One example they use is checking whether a program prints “hello, world.” Even though it sounds simple, there’s no general algorithm that 
can do this for all cases without running into logical contradictions. The section also talks about reductions, where you show that one problem is at least as hard as

read/write head, and a set of rules that determine its behavior. Despite how simple it looks, a Turing Machine can simulate anything a real computer can do. This idea 
is the basis of the Church-Turing Thesis, which says that if something can be computed at all, a Turing Machine can do it. These sections are important because they lay 
out how we define what’s computable and what isn’t—and show that there are problems no computer will ever be able to solve, no matter how advanced technology gets.

\subsection*{Reading Summary and Questions}
Sections 9.1 and 9.2 explore the idea that some problems are beyond what computers can solve, even in theory. In Section 9.1, the book introduces 
a language called $L_d$, which is not recursively enumerable. That means no Turing machine can recognize every string in this language. The authors 
use a technique called diagonalization (similar to a famous proof in math by Cantor) to show this. They list all possible Turing machines and their 
inputs, then build a language that avoids every machine on its own input. Trying to create a machine that accepts exactly this language leads to a 
contradiction, which proves that $L_d$ is truly unrecognizable. Section 9.2 shifts to the universal language $L_u$, which contains all valid program/input 
pairs where the program accepts the input. Unlike $L_d$, this language is recursively enumerable—a Turing machine can recognize it—but it’s still undecidable. 
That means there’s no algorithm that can always say yes or no in a finite amount of time. If the answer is “yes,” the machine will eventually accept it, but 
if it’s “no,” it might run forever. These sections show that some problems can be partially solved, while others are completely out of reach.

\textbf{Exercise 2: Big-O Properties}

Given $f, g, h : \mathbb{N} \to \mathbb{R}_{\geq 0}$:

\begin{enumerate}
    \item $f \in \mathcal{O}(f)$.
    \item $\mathcal{O}(c \cdot f) = \mathcal{O}(f)$ for $c > 0$.
    \item If $f(n) \leq g(n)$ for large $n$, then $\mathcal{O}(f) \subseteq \mathcal{O}(g)$.
    \item If $\mathcal{O}(f) \subseteq \mathcal{O}(g)$, then $\mathcal{O}(f+h) \subseteq \mathcal{O}(g+h)$.
    \item If $h(n) > 0$ and $\mathcal{O}(f) \subseteq \mathcal{O}(g)$, then $\mathcal{O}(f \cdot h) \subseteq \mathcal{O}(g \cdot h)$.
\end{enumerate}

\vspace{1em}
\textbf{Exercise 3: Polynomial and Logarithmic Growth}

\begin{enumerate}

    \item $\mathcal{O}(\log n) \subseteq \mathcal{O}(n)$.
    \item $\mathcal{O}(n \log n) \subseteq \mathcal{O}(n^2)$.
\end{enumerate}

\textbf{Exercise 5: Sorting Algorithm Comparisons}

\textit{Bubble Sort vs. Insertion Sort:}
\begin{itemize}
    \item Worst-case: $\mathcal{O}(n^2)$
    \item Average-case: $\mathcal{O}(n^2)$
    \item Best-case: $\mathcal{O}(n)$ (for insertion sort)
\end{itemize}

\textit{Insertion Sort vs. Merge Sort:}
\begin{itemize}
    \item Insertion sort: $\mathcal{O}(n^2)$ worst/avg, $\mathcal{O}(n)$ best.

\textit{Merge Sort vs. Quick Sort:}
\begin{itemize}
    \item Quick sort: $\mathcal{O}(n^2)$ worst, $\mathcal{O}(n \log n)$ avg/best.
    \item Merge sort: consistently $\mathcal{O}(n \log n)$.
\end{itemize}

\noindent In practice, quick sort tends to be faster due to better memory/cache performance, even though merge sort has a better worst-case guarantee.

way, and why some problems, no matter how important, probably won’t ever have a fast, general solution.
